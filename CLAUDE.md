# zcode-router-kit

> Installable, config-controlled model routing and workflow delegation for [ZCode](https://github.com/zai-org/ZCode).
> Repo: https://github.com/adelvillar1/zcode-router

**Machine-local paths and secrets layout are in `CLAUDE.local.md` (gitignored, auto-loaded alongside this file).** Read it before touching the router runtime, keys, or the launchd service.

## Hard rules (non-negotiable)

- **Never put a raw API key in `roster.json` or any tracked file.** The roster references keys by env-var name only; values live in `~/.zcode/router/.env` (chmod 600). `roster.json` itself IS committed.
- **Never hand-edit the rendered outputs.** `~/.zcode/router/config.json`, `~/.zcode/v2/provider_config.json`, and `~/.zcode/workflows/` are generated by `kit apply` from `roster.json` — edit the roster, then apply.
- **`kit apply --dry-run` before every apply that touches providers or tiers.** Real `apply` backs up `provider_config.json` first and refuses a schema it doesn't understand (`schemaVersion` must be 1); keep that safety chain intact.
- **A `billing: "payg"` provider is never a routing target** unless the roster explicitly sets `allowPayg: true` on it. Registering it for the picker is fine; costing per-token money by default is not.
- **Removing a provider is an explicit `enabled: false` in the roster** — never "the key is missing". A keyless provider must not silently lose a working registration.
- Run `kit doctor` after every apply. Treat a `!` line as something to explain, not noise.
- Default operation target is `master`. Destructive operations (force-push, history rewrite, deleting rendered runtime state) require explicit user approval in the current turn.

## Contracts (the artifacts we treat as commitments)

Three layers of documentation act as contracts and must stay in sync as the codebase evolves. Updating them is part of finishing work, not a separate optional task.

| Contract | Location | Cadence | Purpose |
|----------|----------|---------|---------|
| **Plans** | `docs/plans/YYYY-MM-DD-<slug>.md` | Per feature | Pre-work contract: what we're building, acceptance criteria, linked docs to update |
| **Recaps** | `docs/recaps/SESSION-RECAP-YYYY-MM-DD.md` | Per session | Post-work journal: what shipped, criteria status, doc-update follow-ups |
| **Technical reference** | `TECHNICAL-DOCUMENTATION.md` (top level) | Per feature | Developer-onboarding contract: architecture, API, storage, deployment |
| **Functional reference** | `FUNCTIONAL-SPECIFICATIONS.md` (top level) | Per feature | User-flow contract: behavior, commands, edge cases |

**The cycle is**: draft a plan → implement → write a recap → update the technical and functional contracts. Each phase produces an artifact the next phase consumes. The recap skill prompts for the doc updates explicitly so they don't get skipped.

For trivial changes (typos, single-line fixes, dependency bumps), the cycle compresses: skip the plan, write a brief recap, no contract-doc updates needed. The methodology should match the size of the work.

## Common commands

```bash
npm run kit -- status              # what's installed, which tiers resolved, router health
npm run kit -- doctor [--live]     # full chain verification; changes nothing
npm run kit -- apply --dry-run     # print the planned diff, write nothing
npm run kit -- apply               # render + install + restart + health-check (idempotent)
npm run kit -- workflows list      # library, install state, router-assignability
npm run kit -- workflows sync      # copy the library into ~/.zcode/workflows
npm run kit -- route "…"           # ask the running router for its verdict
npm run kit -- upgrade             # git pull && kit apply
open http://127.0.0.1:8300/dashboard
```

`kit` works directly if the bin is linked; otherwise `node bin/zcode-router-kit.mjs …`.

## Housekeeping protocol — keeps the docs tree from rotting

**You are responsible for keeping the docs tree current.** The whole point of slimming this file was to push reference material into topical files; that only works if those files stay fresh. After every session that changes something material:

1. **Identify which doc(s) the change touched.** Use the "Where to find things" map above. A routing/judge/quota behavior change → the matching `docs/features/*.md`. A new kit command → `TECHNICAL-DOCUMENTATION.md` § Scripts. Key rotation → `CLAUDE.local.md`.

2. **Update the relevant doc inline.** Don't leave the new fact only in a session recap. Recaps are journal entries; topical docs are the source of truth. A recap that says "added X" without updating the corresponding doc is a future drift bug.

3. **Stat tables go in `docs/STATE-SNAPSHOT.md`, not in topical docs.** Counts (workflows, providers, tiers) belong in the dated snapshot file. Topical docs describe *behavior*, not *current totals*. When refreshing the snapshot, **replace** it — do not append.

4. **CLAUDE.md only gets updated when:** a hard rule changes; a new top-level docs area is added; the topology changes; "Today's state" needs a refresh. **Never** add narrative changelogs, "Updated YYYY-MM-DD" markers, or feature deep-dives here.

5. **`CLAUDE.local.md` updates require care.** It's gitignored, so changes leave no trace in `git log`. When you add or rotate a credential or path, **mention it in the session recap**.

5a. **Contract docs (`TECHNICAL-DOCUMENTATION.md`, `FUNCTIONAL-SPECIFICATIONS.md`) must stay in sync with code.** When finishing work on a feature, update the matching section of both. Never declare a feature done while these contracts are stale — track the gap as a known debt in the recap if you must defer.

6. **Drift check before any session ends with non-trivial doc changes:** `wc -l CLAUDE.md` (≤ 300); `git status` must not show `CLAUDE.local.md`; every new `docs/` path mentioned in CLAUDE.md must exist.

7. **When the user reports "Claude pointed at the wrong path" or "asked me for a fact again":** that's a `CLAUDE.local.md` bug. Patch the local file so the next session has it. Do not just answer the question — fix the source.

8. **Quarterly hygiene pass:** re-snapshot `docs/STATE-SNAPSHOT.md` (replace, don't append); archive recaps older than 90 days into `docs/recaps/archive/`; audit topical docs for changelog markers and stat tables.

## Session protocol

**At the start** of any non-trivial session, run `/warmup`. It loads CLAUDE.md, the latest session recap, active plans in `docs/plans/`, and the relevant feature/architecture docs before answering anything.

**At the end** of any session that touched anything, run `/wrapup`. It verifies a recap exists, checks "Today's state" freshness, asks for disposition on uncommitted changes, transitions plan status, escalates deferred-update debts, runs drift checks, and drafts a next-session preview.

For trivial sessions (typo fix, dependency bump, one-line change), skip warmup and skip the recap, but **still run `/wrapup`**.

Otherwise:

1. Read this file (auto-loaded).
2. Read `CLAUDE.local.md` for runtime paths or credentials layout (auto-loaded).
3. For task-specific context, read the relevant `docs/` file from the "Where to find things" map.
4. When changes are made, follow the housekeeping protocol above.

**The six-stage cycle**: `warmup → plan → build → recap → wrapup → next session`. Skip planning for trivial work; skip warmup and recap for trivial sessions; **never skip wrapup** if the session touched anything.
